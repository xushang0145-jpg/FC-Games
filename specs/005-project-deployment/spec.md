# Feature Specification: 项目部署

**Feature Branch**: `005-project-deployment`

**Created**: 2026-06-06

**Status**: Draft

**Input**: User description: "项目部署 — 将 FC 游戏合集网站部署到公网，后续可能会新增个人存档、多人联机功能，需要考虑可拓展性"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 公网访问游戏合集 (Priority: P1)

任何用户在浏览器中输入网址即可打开 FC 游戏合集网站，浏览游戏列表、搜索游戏、选择游戏并开始游玩。部署后的用户体验应与本地开发时一致：游戏列表正常加载、ROM 可正常载入、模拟器运行流畅（60 fps）、音频输出正常。

**Why this priority**: 这是项目部署的核心目标——让用户能通过互联网访问，也是后续所有功能（存档、联机）的基础。

**Independent Test**: 使用手机或电脑浏览器访问部署后的网址，验证游戏列表页正常显示、搜索功能可用、点击游戏可进入模拟器页面并正常游玩。

**Acceptance Scenarios**:

1. **Given** 用户在浏览器地址栏输入网站 URL，**When** 页面加载完成，**Then** 看到 FC 游戏合集首页，显示游戏列表和搜索框
2. **Given** 用户在游戏列表页面，**When** 点击任意游戏卡片，**Then** 进入游戏详情弹窗，可看到游戏名称、截图和开始游戏按钮
3. **Given** 用户在游戏详情弹窗中，**When** 点击开始游戏按钮，**Then** 跳转到游戏页面，模拟器加载对应 ROM 并在 3 秒内进入可玩状态
4. **Given** 用户正在游玩游戏，**When** 按键操作，**Then** 模拟器即时响应，画面流畅无卡顿（60 fps）、声音同步输出
5. **Given** 用户正在游玩游戏，**When** 点击返回按钮，**Then** 返回游戏列表页，列表状态保持（搜索词、滚动位置不变）

---

### User Story 2 - 自动化部署流程 (Priority: P2)

开发者将代码推送到主分支后，部署平台自动构建并发布新版本，无需手动执行构建和上传步骤。构建过程包括：安装依赖、执行代码检查和测试、构建生产包、部署到托管平台。

**Why this priority**: 自动化部署提升开发效率，确保每次发布经过统一的构建和测试流程，避免手动操作导致的人为错误。但 P1 手动部署也可以先上线。

**Independent Test**: 向仓库推送一个包含可见变更的提交（如修改页面标题），验证变更在数分钟内自动反映到线上网站。

**Acceptance Scenarios**:

1. **Given** 开发者向主分支推送新提交，**When** 推送完成，**Then** 部署平台自动触发构建流程
2. **Given** 构建流程被触发，**When** 构建和测试全部通过，**Then** 新版本自动发布到线上
3. **Given** 构建或测试失败，**When** 流程中断，**Then** 线上版本保持不变，开发者收到失败通知

---

### User Story 3 - 可拓展部署架构 (Priority: P3)

部署架构为未来的个人存档和多人联机功能预留扩展能力。当后续需要添加后端服务时，可在不推翻现有部署架构的前提下平滑接入。

**Why this priority**: 当前项目是纯静态站点，不需要后端服务。但用户明确表示后续会新增存档和联机功能，提前做架构预留可以避免未来大规模重构。此项不阻塞 P1 和 P2 上线。

**Independent Test**: 审查部署架构文档，确认其描述了如何在不改变现有静态资源部署方式的前提下接入后端 API 服务。

**Acceptance Scenarios**:

1. **Given** 部署架构已落地，**When** 审查其设计，**Then** 确认静态资源和未来 API 服务的部署路径可以共存且不互相冲突
2. **Given** 部署架构已落地，**When** 后续新增存档功能需要后端 API，**Then** 可以在不修改现有静态页面部署流程的情况下接入后端服务
3. **Given** 部署架构已落地，**When** 后续新增多人联机功能需要 WebSocket 长连接，**Then** 可以在不修改现有静态页面部署流程的情况下接入实时通信服务

---

### Edge Cases

- 80+ 个 ROM 文件总大小约 15MB，首次加载游戏列表时是否需要分页/懒加载以避免一次性传输过多资源？
- 如果部署平台对静态文件数量或单文件大小有上限，如何处理 ROM 文件的存放？
- 用户网络环境较差时（如移动 3G/4G），单个 ROM 最大约 400KB，加载是否在可接受时间内？
- 部署后如果 ROM 文件名包含中文字符，URL 编码在 CDN/服务器上的兼容性如何？
- 静态资源和未来 API 服务不在同一域名时，CORS 配置如何提前规划？
- 部署平台提供的 HTTPS 证书是否覆盖自定义域名？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 构建为纯静态资源（HTML、JavaScript、CSS、ROM 文件），无需服务端运行时即可被浏览器完整加载和运行
- **FR-002**: 系统 MUST 支持通过标准静态资源托管服务部署，用户输入 URL 即可访问完整功能的 FC 游戏合集网站
- **FR-003**: 所有静态资源（含 ROM 文件）MUST 通过 HTTPS 提供服务，确保浏览器安全策略不被阻断
- **FR-004**: 部署后的网站 MUST 在现代浏览器（Chrome、Firefox、Safari、Edge 最近 2 个主版本）上功能完整且性能达标
- **FR-005**: 构建流程 MUST 包含自动化测试（单元测试 + E2E 测试），所有测试通过后方可部署
- **FR-006**: 代码推送到主分支后 MUST 自动触发构建和部署流程，无需人工干预
- **FR-007**: 构建失败时 MUST 阻止部署，并通过 GitHub 原生通知（邮件 + 通知中心）告知仓库 owner
- **FR-008**: 系统 MUST 支持自定义域名绑定和 HTTPS 证书自动管理
- **FR-009**: 部署架构 MUST 预留 API 服务接入能力（将来用于个人存档功能），前端可通过配置切换 API 端点
- **FR-010**: 部署架构 MUST 预留 WebSocket 长连接接入能力（将来用于多人联机功能），前端可通过配置切换实时通信端点
- **FR-011**: API 和 WebSocket 端点配置 MUST 在构建时注入，支持按部署环境（开发/生产）差异化设置

### Key Entities

- **静态资源**: HTML 入口文件、JavaScript 模块、CSS 样式表、游戏 ROM 文件（.nes），所有内容在构建阶段确定，部署后内容不变
- **部署环境**: 开发环境（本地开发服务器）、生产环境（远程托管平台），通过环境变量或构建配置区分
- **服务端点配置**: API 基础 URL、WebSocket 连接地址，构建时注入的配置项，当前为空（纯静态模式），未来填入后端服务地址

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从输入 URL 到看到完整游戏列表页面的时间不超过 5 秒（含所有首屏资源加载）
- **SC-002**: 部署后的游戏模拟器与本地开发环境表现一致，稳定运行在 60 fps
- **SC-003**: 从代码推送到线上更新完成的总时间不超过 10 分钟
- **SC-004**: 网站首页和游戏页面的 Lighthouse Performance 评分不低于 90 分
- **SC-005**: 任意单个 ROM 文件（最大约 400KB）在 4G 网络下加载完成时间不超过 3 秒
- **SC-006**: 部署后的网站在无服务端的情况下可完整运行所有现有功能（游戏列表浏览、搜索、ROM 加载、模拟器游玩）
- **SC-007**: 通过一次配置修改即可为所有页面启用/切换 API 或 WebSocket 端点，无需逐个页面修改代码

## Clarifications

### Session 2026-06-06

- Q: 部署平台选型优先级——优先免费方案（后续迁移），还是优先原生支持前后端一体化（后续扩展无需迁移）？ → A: 优先前后端一体化支持好的平台（如 Vercel/Netlify），即使免费额度有限，后续扩展无需迁移
- Q: 构建失败时通过什么方式通知开发者？ → A: GitHub 原生通知（构建失败时自动通知仓库 owner，邮件 + GitHub 内通知）

## Dependencies

- 需要选择一个支持前后端一体化的静态托管平台（须满足：自定义域名、HTTPS 自动颁发、CI/CD 集成、Serverless Function 支持用于后期后端扩展、WebSocket 支持或可搭配实时通信服务、足够的带宽和存储空间容纳 15MB+ ROM 文件）
- ROM 文件（`roms/` 目录，88 个 .nes 文件，总大小约 15MB）为必需静态资源

## Assumptions

- 部署平台选型优先考虑原生支持前后端一体化的服务（如 Vercel/Netlify），后续添加后端 API 和 WebSocket 时无需迁移平台
- 目标用户的网络环境为宽带或 4G 及以上
- 自定义域名由用户自行购买和管理（DNS 配置）
- 当前版本不包含后端服务，纯静态部署足以满足 P1 需求
- 未来存档功能将使用独立的后端 API 服务（RESTful），联机功能将使用独立的 WebSocket 服务
- 前端已预留 API 端点配置机制（通过构建时注入的环境变量），无需在本功能中实现具体的多环境构建方案
