# M1 产品需求文档：存档/读档与继续游戏

**Feature Branch**: `FCG-5-m1-savestate`

**Created**: 2026-06-13

**Status**: Draft（待老赵评审）

**关联 Issue**: [FCG-5](mention://issue/105299e7-7f06-4c39-92d4-173ce15ccd18)

## 1. 背景与目标

FC-Games 进入 M1「稳定可玩的 v1.1」阶段。本 PRD 负责把「存档/读档」「继续游戏」「运营仪表盘访问控制」「默认键位优化」四个需求转化为可开发、可验收的产品方案。

### 1.1 目标

- 让用户在游戏过程中可以随时保存进度、读取进度，降低 NES 游戏高难度带来的挫败感。
- 在首页/列表页提供「继续游戏」入口，让用户一键回到最近游玩的游戏与进度。
- 为运营仪表盘增加最低成本的访问控制，防止运营数据被公开访问。
- 统一并同步默认键位说明，减少用户进入游戏后的学习成本。

### 1.2 范围边界

**In Scope**

- 每款游戏的本地存档/读档（localStorage）。
- 首页「继续游戏」入口。
- 游戏页/详情页的继续游玩体验。
- 运营仪表盘密码保护。
- 默认键位文档同步（Start=Digit1 / Select=Digit2）。

**Out of Scope (M1)**

- 云端存档同步、跨设备存档、存档分享。
- 多用户账户体系。
- Supabase Auth 登录仪表盘（列为 M2 可选项）。
- 存档压缩/加密、存档导入导出。

## 2. 用户故事与验收标准

### User Story 1 - 存档与读档（P1）

作为一名玩家，我希望在游戏过程中随时保存和读取进度，以便在失败后能快速回到之前的进度，而不需要从头开始。

**Why this priority**: 这是 M1 的核心价值；没有存档功能，FC 游戏的高难度会劝退大量用户。

**Independent Test**: 启动任意游戏，按存档快捷键保存，重启页面后按读档快捷键，应能恢复到保存时的画面与状态。

**Acceptance Scenarios**:

1. **Given** 用户正在游戏页游玩，**When** 用户触发存档快捷键（默认 `F2`）或点击「存档」按钮，**Then** 系统把当前 NES 状态写入该游戏的本地存档槽，并显示「存档成功」提示。
2. **Given** 用户已保存过进度，**When** 用户触发读档快捷键（默认 `F4`）或点击「读档」按钮，**Then** 系统读取本地存档并恢复到保存时的游戏状态，画面/音频无缝衔接。
3. **Given** 用户已有存档并再次执行存档，**When** 当前存档槽已存在数据，**Then** 系统弹窗提示「是否覆盖已有存档」，用户确认后才覆盖，取消则保留原存档。
4. **Given** 用户执行读档，**When** 存档数据损坏、与当前 ROM 不匹配或存档版本不兼容，**Then** 系统提示「读档失败，已为您重新开始游戏」，并恢复到 ROM 初始状态，不崩溃。
5. **Given** 用户通过「继续游戏」入口进入游戏，**When** 系统检测到存在自动存档，**Then** 直接恢复自动存档；若无自动存档，则从 ROM 开头开始。

---

### User Story 2 - 继续游戏入口（P1）

作为一名玩家，我希望打开网站后能快速回到上次玩的游戏，而不是重新搜索或翻页。

**Why this priority**: 直接提升回访用户的启动效率，是 v1.1 留存体验的关键入口。

**Independent Test**: 游玩任意游戏后返回首页，应出现「继续游戏」区域，点击后直接进入该游戏并恢复进度。

**Acceptance Scenarios**:

1. **Given** 用户曾经游玩过至少一款游戏，**When** 用户访问首页，**Then** 首页顶部出现「继续游戏」卡片，展示最近游玩游戏名称与相对时间（如「3 分钟前」）。
2. **Given** 用户点击「继续游戏」卡片，**When** 跳转至游戏页，**Then** 自动加载对应 ROM 并恢复最新的自动存档；若没有自动存档，则从 ROM 开头开始。
3. **Given** 用户从未游玩过任何游戏，**When** 访问首页，**Then** 不显示「继续游戏」区域，首页保持原有列表视图。
4. **Given** 用户在详情浮层中打开最近玩过的游戏，**When** 存在该游戏存档，**Then** 开始按钮文案为「▶ 继续游戏」并展示「上次进度可恢复」提示；无存档时文案为「▶ 开始游戏」。

---

### User Story 3 - 运营仪表盘访问控制（P2）

作为运营人员，我希望运营仪表盘不会被公开访问，只有知道密码的人才能查看数据。

**Why this priority**: 当前 `stats.html` 无访问限制，存在数据泄露风险；M1 需先加一道最低成本保护。

**Independent Test**: 在无痕窗口访问 `stats.html`，未输入正确密码前看不到任何数据；输入正确密码后可正常查看。

**Acceptance Scenarios**:

1. **Given** 用户访问 `stats.html`，**When** 环境变量 `VITE_DASHBOARD_PASSWORD_HASH` 已配置，**Then** 页面先显示密码输入弹窗，输入正确密码后把验证状态写入 `sessionStorage` 并展示仪表盘。
2. **Given** 密码输入错误，**When** 用户点击确认，**Then** 显示「密码错误」提示，不展示数据，3 秒内不可重复提交。
3. **Given** 环境变量 `VITE_DASHBOARD_PASSWORD_HASH` 未配置，**When** 访问 `stats.html`，**Then** 页面跳过密码验证直接展示数据（便于本地开发/测试）。
4. **Given** 用户已通过验证，**When** 在当前会话内刷新页面或切换时间范围，**Then** 不需要重新输入密码。
5. **Given** 用户关闭标签页后重新打开，**When** 再次访问 `stats.html`，**Then** 需要重新输入密码（`sessionStorage` 会话级）。

---

### User Story 4 - 默认键位优化与文档同步（P2）

作为一名玩家，我希望在开始游戏前就能看到准确的默认键位说明，避免进入游戏后试键。

**Why this priority**: 当前 `game-page.mockup.html` 中 Start/Select 仍显示 Enter/RightShift，与代码默认的 Digit1/Digit2 不一致，会造成用户困惑。

**Independent Test**: 详情浮层、按键设置面板、帮助提示中的默认键位全部与 `input.js` 中 `DEFAULT_BINDINGS` 一致。

**Acceptance Scenarios**:

1. **Given** 用户打开游戏详情浮层，**When** 查看「按键操作」区域，**Then** 默认显示：上 W / 下 S / 左 A / 右 D / A 按钮 K / B 按钮 J / A 连发 I / B 连发 U / Start 1 / Select 2。
2. **Given** 用户在游戏页打开「按键设置」面板，**When** 查看默认键位，**Then** Start 显示为 `1`，Select 显示为 `2`，无 Enter/Shift 残留。
3. **Given** 用户首次进入游戏页，**When** 页面加载完成，**Then** 若该游戏无自定义键位，则自动使用上述默认键位，且详情浮层与按键面板读取的是同一默认配置源。
4. **Given** 默认键位文档发生变更，**When** 修改 `input.js` 中的 `DEFAULT_BINDINGS`，**Then** 详情浮层与按键面板无需额外修改即可同步（避免硬编码二义）。

## 3. 功能需求

### 3.1 存档/读档

- **FR-001**: 系统必须为每款游戏维护两类本地存档：
  - **自动存档（auto）**：在用户离开游戏页（`beforeunload` / `pagehide`）或游戏运行中按固定周期（建议 30 秒）自动保存。
  - **手动存档（manual）**：用户通过快捷键 `F2` 或顶部「存档」按钮主动保存。
- **FR-002**: 每款游戏在 localStorage 中仅保留 **1 个自动存档 + 1 个手动存档槽**，避免超出浏览器存储配额。
- **FR-003**: 手动存档覆盖前必须弹出确认弹窗；自动存档直接覆盖，不打扰用户。
- **FR-004**: 读档入口包括快捷键 `F4`、顶部「读档」按钮、首页/详情页「继续游戏」。
- **FR-005**: 读档前必须校验存档元数据：ROM 文件名、存档版本号、CRC/长度。校验失败时给出明确错误提示并恢复 ROM 初始状态。
- **FR-006**: 存档/读档操作不得阻塞主线程，序列化/反序列化应在暂停或游戏循环间隙执行，稳定 60 fps 不下降。
- **FR-007**: 当 localStorage 写满时，系统应提示「存档失败：本地空间不足」，并保留上一次成功的存档。

### 3.2 继续游戏

- **FR-008**: 首页顶部新增「继续游戏」区域，仅当 `fc_play_history` 中存在记录时显示。
- **FR-009**: 「继续游戏」卡片展示最近游戏名称、图标、相对时间，点击后跳转至 `/game.html?rom=<file>&continue=1`。
- **FR-010**: 游戏页解析 `continue=1` 参数时，优先恢复自动存档；无自动存档则从 ROM 初始状态开始。
- **FR-011**: 用户通过普通入口（无 `continue=1`）开始游戏时，不自动恢复存档，保证「重新开始」语义清晰。

### 3.3 运营仪表盘访问控制

- **FR-012**: `stats.html` 加载数据前，先检查 `sessionStorage` 中是否存在 `dashboard_auth` 标记。
- **FR-013**: 若未认证且环境变量 `VITE_DASHBOARD_PASSWORD_HASH` 已配置，渲染密码弹窗；用户输入后在前端做 SHA-256 哈希比对。
- **FR-014**: 若环境变量未配置，则跳过认证，直接渲染仪表盘。
- **FR-015**: 密码验证成功后写入 `sessionStorage`，当前会话免密；关闭标签页后失效。
- **FR-016**: 连续输错 5 次后，锁定当前会话的密码输入（刷新后可重试）。

### 3.4 默认键位文档同步

- **FR-017**: 统一默认键位源为 `input.js` 中的 `DEFAULT_BINDINGS`。
- **FR-018**: 详情浮层 `detail-modal.js` 不再维护独立的 `DEFAULT_BINDINGS`，改为从 `input.js` 导入或调用 `loadBinding(game.id)`。
- **FR-019**: 更新 `nimbalyst-local/mockups/game-page.mockup.html` 中的键位示例，使其与代码一致。
- **FR-020**: 在游戏页增加可唤出的「帮助」提示（如按 `H` 或点击帮助按钮），展示当前键位图。

## 4. 关键实体

- **Savestate（存档）**
  - `romId`: ROM 文件名，用于匹配游戏。
  - `slot`: `"auto" | "manual"`。
  - `version`: 存档格式版本号（与 `jsnes` 状态结构绑定）。
  - `createdAt`: ISO 8601 时间戳。
  - `state`: `jsnes` 实例 `toJSON()` 的序列化结果。
- **PlayRecord（游玩记录）**
  - 复用现有 `fc_play_history` 结构：`{ "romFile.nes": "2026-06-13T..." }`。
- **DashboardAuth（仪表盘认证）**
  - 存储于 `sessionStorage`，值为简单布尔/时间戳对象，避免每次刷新重复输入。

### 5.1 首页「继续游戏」区域

```
┌─────────────────────────────────────────────┐
│  FC 游戏合集                        共 88 款 │
├─────────────────────────────────────────────┤
│ 🔍 搜索游戏名称...                           │
├─────────────────────────────────────────────┤
│ [▶ 继续游戏] 超级玛莉 · 3 分钟前             │
├─────────────────────────────────────────────┤
│ [全部] [⭐ 最近玩过]                          │
│  🍄 超级玛莉    🔫 魂斗罗  ...               │
└─────────────────────────────────────────────┘
```

- 仅 1 个卡片，展示最近游玩的游戏。
- 点击整张卡片跳转并恢复进度。
- 若最近游戏无自动存档，卡片仍显示，进入后从 ROM 开头开始。

### 5.2 游戏页顶部栏

在现有顶部栏右侧、「按键设置」按钮左侧新增两个图标按钮：

```
← 返回列表          超级玛莉              💾 存档  📂 读档  🎮 按键设置
```

- **存档按钮**：点击后保存到手动槽；若已有手动存档，弹窗确认覆盖。
- **读档按钮**：点击后从手动槽恢复；无手动存档时按钮置灰并提示「暂无手动存档」。
- **快捷键提示**：按钮 hover 显示快捷键 `F2 / F4`。

### 5.3 存档/读档面板（移动端 / 虚拟手柄）

在虚拟手柄区域增加一个「菜单」按钮，点击后底部弹出：

```
┌─────────────────────────────┐
│  存档  │  读档  │  返回游戏  │
└─────────────────────────────┘
```

- 自动存档在菜单中显示为「自动：3 分钟前」。
- 手动存档显示为「手动：刚刚」。

### 5.4 读档失败处理

当读档失败时，在游戏画面中央显示非模态 toast：

```
⚠ 读档失败：存档损坏或版本不兼容，已重新开始游戏。
```

3 秒后自动消失，不影响当前游戏操作。

### 5.5 运营仪表盘密码弹窗

```
┌─────────────────────────────┐
│  FC 运营分析 - 需要访问密码   │
│                             │
│  请输入密码                  │
│  [________________]         │
│                             │
│         [确认]              │
│  ⚠ 密码错误                 │
└─────────────────────────────┘
```

- 密码输入框类型为 `password`。
- 错误提示在确认后立即显示。
- 未输入密码前，页面主体内容不渲染，避免数据泄露。

## 6. 非功能需求

- **性能**: 存档序列化不得导致可感知的卡顿；在 `requestIdleCallback` 或暂停时执行，目标帧率保持 60 fps。
- **存储**: 单游戏存档控制在 ~500 KB 以内；localStorage 总占用超过 4 MB 时给出清理提示。
- **兼容性**: 继续游戏与存档功能在 Chrome/Firefox/Safari/Edge 最近 2 个主版本可用；移动端支持虚拟手柄菜单。
- **隐私**: 存档数据仅保存在用户本地浏览器，不上传云端。
- **可维护性**: 默认键位、存档版本号、认证配置均集中为单一事实来源，避免多处硬编码。

## 7. 决策记录

| 决策项 | 选定方案 | 备选方案 | 理由 |
| --- | --- | --- | --- |
| 存档存储位置 | 浏览器 localStorage | IndexedDB / 服务端 | 零依赖、离线可用、与现有键位存储一致；单游戏单槽控制大小。 |
| 手动存档槽数 | 1 个手动 + 1 个自动 | 多槽位 | M1 先验证核心价值，降低 UI/存储复杂度。 |
| 继续游戏数据来源 | 自动存档 | 手动存档 | 自动存档是用户离开时的真实进度，最符合「继续」预期。 |
| 仪表盘访问控制 | 静态密码（SHA-256 环境变量） | Supabase Auth | M1 仅需保护数据不被公开访问，密码门成本最低；Supabase Auth 列为 M2 可选项。 |
| Start/Select 默认键 | Digit1 / Digit2 | Enter / Shift | 已在线上代码实现，避免与浏览器/输入法冲突，PRD 确认并同步文档。 |

## 8. 成功指标

- **SC-001**: 玩家能在 2 秒内完成一次手动存档/读档操作（含视觉反馈）。
- **SC-002**: 回访用户通过首页「继续游戏」进入游戏的比例 ≥ 30%（埋点追踪 `continue_entry` 事件）。
- **SC-003**: 存档/读档失败率 < 1%（通过错误事件埋点统计）。
- **SC-004**: 运营仪表盘在未认证情况下不暴露任何 KPI/表格数据（安全测试通过）。
- **SC-005**: 默认键位说明与代码实现 100% 一致（人工走查 + E2E 截图比对）。

## 10. 待确认事项

以下问题需要老赵/开发在评审会上确认：

1. 手动存档快捷键 `F2` / 读档 `F4` 是否符合目标用户习惯？是否需要提供 `Ctrl+S`/`Ctrl+L` 作为备用？
2. 自动存档周期是否设为 30 秒，还是仅在离开页面时保存一次？
3. 运营仪表盘密码是否由运维人员单独配置环境变量，还是需要在部署文档中补充说明？
4. M1 是否需要为每款游戏提供「删除存档」功能？
5. 是否需要把 `nimbalyst-local/mockups/stats-dashboard.mockup.html` 中的访问控制原型同步更新？
