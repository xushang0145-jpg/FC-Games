# Feature Specification: 埋点数据统计

**Feature Branch**: `006-analytics-tracking`

**Created**: 2026-06-06

**Status**: Draft

**Input**: User description: "埋点：数据统计"

## Clarifications

### Session 2026-06-06

- **Q**: 统计仪表盘页面如何访问？ → **A**: 直接通过 URL 访问（如 `/admin` 或 `/stats.html`），不在首页或游戏页放置任何入口链接
- **Q**: 游戏启动事件的触发时机？ → **A**: 用户点击"开始"按钮后触发（游戏模拟器真正开始运行时）
- **Q**: 会话（session）如何定义？ → **A**: 按页面生命周期：每次页面加载生成新会话 ID，关闭/导航即结束
- **Q**: 数据存储架构？ → **A**: 埋点数据主存储改为 Supabase；网络失败时暂存 localStorage，恢复后批量上报
- **Q**: 网络恢复后暂存数据何时上报？ → **A**: 页面加载时检查 localStorage 暂存队列，有数据则批量上报

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 页面浏览追踪 (Priority: P1)

作为网站运营者，我希望了解用户访问了哪些页面，以便分析用户流量分布和热门内容。

**Why this priority**: 页面浏览是最基础的埋点数据，是所有后续分析的前提。没有浏览数据，就无法了解用户从何而来、去了哪里。

**Independent Test**: 可以独立测试——在任意页面打开浏览器开发者工具，查看 localStorage 中是否记录了页面浏览事件，包括页面路径、时间戳和访问次数。

**Acceptance Scenarios**:

1. **Given** 用户首次访问首页，**When** 页面加载完成，**Then** 系统记录一条首页浏览事件，包含页面路径和当前时间戳
2. **Given** 用户从首页跳转到游戏详情页，**When** 详情页加载完成，**Then** 系统记录一条详情页浏览事件，且首页浏览数据不被覆盖
3. **Given** 用户在同一会话中多次刷新同一页面，**When** 每次刷新完成，**Then** 该页面的浏览次数正确累加

---

### User Story 2 - 游戏交互追踪 (Priority: P1)

作为网站运营者，我希望了解用户玩了哪些游戏、玩了多长时间，以便评估游戏受欢迎程度和用户参与度。

**Why this priority**: 游戏交互数据是核心业务指标，直接反映用户对游戏内容的兴趣。游戏时长数据对判断游戏质量尤为重要。

**Independent Test**: 可以独立测试——启动任意游戏，在浏览器开发者工具中查看是否记录了游戏启动事件；游玩一段时间后退出，查看是否记录了游戏时长数据。

**Acceptance Scenarios**:

1. **Given** 用户在首页点击某款游戏的「开始游戏」按钮，**When** 用户点击"开始"按钮后游戏模拟器开始运行，**Then** 系统记录一条该游戏的启动事件
2. **Given** 用户正在游玩某款游戏，**When** 用户点击退出或返回首页，**Then** 系统记录该次游玩的总时长（精确到秒）
3. **Given** 用户在短时间内多次启动同一款游戏，**When** 每次启动和退出都被记录，**Then** 该游戏的总游玩次数和总游玩时长正确累加

---

### User Story 3 - 数据统计仪表盘 (Priority: P2)

作为网站运营者，我希望能在一个专门的页面查看所有埋点数据的汇总报告，以便快速了解网站运营状况。

**Why this priority**: 原始事件数据可读性差，需要汇总和可视化才能产生洞察。但数据统计仪表盘依赖 P1 的数据收集功能，因此优先级略低。

**Independent Test**: 可以独立测试——在产生一定量的浏览和游戏数据后，访问统计仪表盘页面，验证各项数据汇总和展示的准确性。

**Acceptance Scenarios**:

1. **Given** 网站已产生一定数量的浏览和游戏数据，**When** 运营者访问统计仪表盘页面，**Then** 页面展示各页面的总浏览次数、各游戏的总启动次数和总游玩时长
2. **Given** 统计仪表盘页面已展示数据，**When** 运营者按「今日」、「本周」、「本月」筛选时间范围，**Then** 页面只展示对应时间范围内的统计数据
3. **Given** 统计仪表盘页面无数据可展示，**When** 运营者访问该页面，**Then** 页面展示友好的空状态提示，而非空白或错误

---

### User Story 3.5 - 用户特征分析 (Priority: P2)

作为网站运营者，我希望了解用户的终端类型和地理位置分布，以便优化网站适配和了解用户群体构成。

**Why this priority**: 用户特征数据（终端、地域）是运营分析的重要维度，能帮助判断是否需要优化移动端体验、了解核心用户分布区域。与仪表盘同为 P2，可并行开发。

**Independent Test**: 可以独立测试——在产生数据后，检查统计仪表盘是否展示终端分布（Desktop/Mobile/Tablet）和地域分布（国家/省份/城市）。

**Acceptance Scenarios**:

1. **Given** 用户从 PC 浏览器访问网站，**When** 页面加载完成，**Then** 系统记录的页面浏览事件包含 `device_type: "desktop"`
2. **Given** 用户从手机浏览器访问网站，**When** 页面加载完成，**Then** 系统记录的页面浏览事件包含 `device_type: "mobile"`
3. **Given** 网站已产生一定量的浏览数据，**When** 运营者访问统计仪表盘页面，**Then** 页面展示终端类型分布（各类型占比）
4. **Given** 网站已产生一定量的浏览数据，**When** 运营者访问统计仪表盘页面，**Then** 页面展示 Top 10 访问城市排行榜

---

### User Story 4 - 数据导出 (Priority: P3)

作为网站运营者，我希望能够将埋点数据导出为标准格式，以便使用外部工具进行深度分析。

**Why this priority**: 数据导出是高级功能，用于与外部 BI 工具集成。大多数分析需求可通过内置仪表盘满足，因此优先级较低。

**Independent Test**: 可以独立测试——在产生数据后，点击导出按钮，验证生成的文件内容完整且格式正确。

**Acceptance Scenarios**:

1. **Given** 网站已产生埋点数据，**When** 运营者在统计页面点击「导出数据」按钮，**Then** 系统生成并下载一个包含所有原始事件数据的 JSON 文件
2. **Given** 运营者选择了特定时间范围后点击导出，**When** 文件下载完成，**Then** 文件中只包含该时间范围内的事件数据

---

### Edge Cases

- **浏览器隐私模式/无痕模式**: localStorage 在无痕模式下仍然可用，但数据不会持久化到磁盘。用户关闭无痕窗口后数据丢失是预期行为
- **同一用户多设备访问**: 每个设备/浏览器独立生成 `user_id`，数据汇聚到 Supabase 但不同设备的 `user_id` 不同。运营者看到的统计中，同一人的多个设备会被计为多个独立访客
- **用户手动清除浏览器数据**: 所有埋点数据将被清除，这是预期行为
- **长时间挂机**: 用户启动游戏后长时间不操作（超过 30 分钟），系统应将超时时长截断至合理上限，避免异常时长数据扭曲统计结果
- **页面意外关闭**: 若用户在游戏中直接关闭标签页或浏览器，系统应在页面 `beforeunload` 事件中尽力记录游戏时长，确保数据不丢失
- **网络连接中断**: 若用户网络不可用，埋点数据暂存 localStorage（上限 100 条），网络恢复后自动批量上报；超出上限时丢弃最旧数据
- **Supabase 服务不可用**: 若 Supabase 临时故障，系统按网络中断逻辑降级处理，不阻断核心游戏体验
- **IP 定位失败**: 若 IP 定位 API 不可用或返回错误，地理位置字段留空（`null`），不影响其他数据记录
- **用户代理解析失败**: 若 `navigator.userAgent` 无法解析，终端类型默认记录为 `desktop`
- **VPN/代理用户**: 通过 IP 定位获取的地理位置可能不准确，这是预期限制

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在每次页面加载完成时自动记录一条页面浏览事件，包含页面路径和访问时间戳
- **FR-002**: 系统 MUST 在用户点击"开始"按钮、游戏模拟器真正开始运行后记录一条游戏启动事件，包含游戏名称和启动时间戳
- **FR-003**: 系统 MUST 在用户退出游戏或离开游戏页面时记录该次游玩的总时长（秒）
- **FR-004**: 系统 MUST 将埋点数据实时发送到 Supabase 数据库存储；网络不可用时 MUST 暂存到 localStorage，网络恢复后自动批量上报
- **FR-005**: 系统 MUST 提供统计仪表盘页面（独立页面，通过直接 URL 访问，不嵌入主站导航），汇总展示页面浏览次数、游戏启动次数和总游玩时长
- **FR-006**: 统计仪表盘 MUST 支持按时间范围筛选数据（今日、本周、本月、全部）
- **FR-007**: 系统 MUST 在游戏单次游玩时长超过 30 分钟时，将时长截断记录为 30 分钟
- **FR-008**: 系统 MUST 在页面 `beforeunload` 事件中记录未正常退出的游戏时长
- **FR-009**: 当 Supabase 写入失败（网络中断、服务不可用）时，系统 MUST 将事件暂存到 localStorage 队列；下次页面加载时检查并批量上报；暂存数据上限为 100 条，超出时丢弃最旧数据
- **FR-010**: 系统 MUST 在首次访问时生成一个匿名 `user_id`（UUID），持久化存储在 localStorage 中，后续所有事件 MUST 携带该 `user_id`
- **FR-011**: 系统 MUST 在记录页面浏览事件时，自动检测并记录用户终端类型（`desktop` / `mobile` / `tablet`）
- **FR-012**: 系统 MUST 在记录页面浏览事件时，通过 IP 定位 API 获取并记录用户地理位置（国家、省份、城市）
- **FR-013**: 统计仪表盘 MUST 展示终端类型分布（各类型占比饼图/条形图）
- **FR-014**: 统计仪表盘 MUST 展示 Top 10 访问城市排行榜
- **FR-015**: 统计仪表盘 SHOULD 展示独立访客数（UV，按 user_id 去重）
- **FR-016**: 系统 SHOULD 提供数据导出功能，将原始事件数据导出为 JSON 格式文件

### Key Entities *(include if feature involves data)*

- **页面浏览事件 (PageViewEvent)**: 代表一次页面访问，包含匿名用户标识（`user_id`，首次访问生成并持久化）、页面路径（如 `/`、`/games/超级玛莉`）、访问时间戳、会话标识（页面加载时生成，页面关闭或导航即失效）、终端类型（`desktop`/`mobile`/`tablet`）、地理位置（国家/省份/城市）
- **游戏启动事件 (GameStartEvent)**: 代表一次游戏启动，包含匿名用户标识（`user_id`）、游戏名称、启动时间戳、会话标识（与当前页面会话一致）、终端类型、地理位置
- **游戏时长事件 (GameDurationEvent)**: 代表一次完整的游戏游玩，包含匿名用户标识（`user_id`）、游戏名称、启动时间戳、结束时间戳、游玩时长（秒）、终端类型、地理位置
- **统计数据 (AggregatedStats)**: 汇总后的数据视图，包含各页面的浏览次数、各游戏的启动次数和总时长、终端类型分布、Top 城市排行，按时间范围过滤

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 页面浏览事件的记录成功率达到 100%（即每次页面加载都产生对应事件）
- **SC-002**: 游戏启动事件的记录成功率达到 100%（即每次游戏成功加载都产生对应事件）
- **SC-003**: 游戏时长数据的记录完整率达到 95% 以上（考虑页面意外关闭等不可控场景）
- **SC-004**: 统计仪表盘的数据汇总计算准确率达到 100%（汇总结果与原始事件数据一致）
- **SC-005**: 埋点数据收集对 NES 模拟器 60 fps 渲染性能无可见影响（帧率波动不超过 1 fps）
- **SC-006**: 统计仪表盘页面加载时间不超过 2 秒（在已存储 1000 条事件数据的场景下）

## Assumptions

- 用户使用现代浏览器，支持 fetch API 和 localStorage
- 用户设备 MOST OF THE TIME 有网络连接，Supabase 可正常访问
- 数据通过 Supabase 集中存储，统计仪表盘通过 API 查询汇总数据
- 统计仪表盘页面仅供运营者访问，暂不做访问权限控制
- 数据保留策略：事件数据保留最近 90 天，超期数据自动清理
- 埋点代码采用轻量实现，避免阻塞主线程；Supabase 作为后端存储，不引入外部分析 SDK
- 网络中断时通过 localStorage 降级暂存，确保事件不丢失
